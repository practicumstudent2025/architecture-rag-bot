<summary><strong>Контекст задачи</strong></summary>

QuantumForge Software — финско-эстонская продуктовая компания, которой требуется интеллектуальный бот для работы с корпоративной базой знаний:
- ~18,000 Markdown/MDX файлов в репозиториях
- ~3,000 страниц Confluence (30 пространств)
- ~250 PDF-спецификаций
- Прирост ~400 страниц в месяц

**Текущая архитектура компании:**

| Слой | Технологии и сервисы | Где лежат документы |
|------|---------------------|---------------------|
| Продакшн | AWS (EKS + RDS) + облачные технологии (фронтовые edge‑ноды) | Terraform state, Helm charts |
| CI/CD | GitHub Actions, Jenkins (legacy), ArgoCD | GitHub Wiki, README |
| Общение | Slack, Jira, Confluence, Miro | Confluence, Google Drive |
| Код | Monorepo (GitHub); microservices на Python/Go/Node | CODEOWNERS, ADR (Markdown) |
| Данные | Kafka, ClickHouse, Snowflake | dbt‑доки, ER‑диаграммы |
| Служба поддержки | Zendesk + Statuspage | Zendesk Guide, Google Docs |

**Источники документов для RAG-бота:**
1. **GitHub** - 18,000 Markdown/MDX файлов (monorepo, CODEOWNERS, ADR, README, GitHub Wiki)
2. **Confluence** - 3,000 страниц (30 пространств)
3. **PDF-файлы** - 250 спецификаций (наследие заказных проектов)
4. **Google Drive** - дополнительные документы
5. **Zendesk Guide** - документация службы поддержки
6. **Google Docs** - регламенты и бизнес-правила

**Динамика роста:**
- Текущий объем: ~21,250 документов (18,000 + 3,000 + 250)
- Прирост: ~400 страниц/месяц
- Прогноз через год: ~26,050 документов
- Прогноз через 3 года: ~35,650 документов

**Функции и роли пользователей базы знаний:**

1. **Разработчики** — ищут:
   - Архитектурные решения (ADR - Architecture Decision Records)
   - API-документацию
   - Описание микросервисов
   - Источники: GitHub (CODEOWNERS, ADR, README), Confluence (техническая документация)

2. **Саппорт** — ищут:
   - Способы решения типовых проблем пользователей
   - Troubleshooting гайды
   - Источники: Zendesk Guide, Confluence (база знаний поддержки), GitHub (issues, troubleshooting docs)

3. **Менеджеры и аналитики** — ищут:
   - Регламенты
   - Бизнес-правила
   - Процессы и политики
   - Источники: Google Docs, Confluence (бизнес-пространства), PDF-регламенты

4. **Новые сотрудники** — ищут:
   - Onboarding-инструкции
   - Процессы адаптации
   - Общую информацию о компании и продуктах
   - Источники: Confluence (onboarding пространства), Google Drive, README файлы

**Требования к решению с учетом ролей пользователей:**
- Поддержка фильтрации по типам документов (технические, бизнес, onboarding)
- Разные промпты для разных ролей (технические vs бизнес-вопросы)
- Приоритизация источников в зависимости от типа запроса
- Поддержка метаданных для категоризации документов по аудитории

**Существующие проблемы компании и как RAG-бот их решает:**

1. **Разрозненность и дубли:**
   - **Проблема:** База знаний растёт, но плохо структурирована. Одни и те же процессы описаны в Confluence, Notion и PDF-регламентах, но расходятся по версиям. Руководство не может объективно оценить, что важно, а что требует доработки.
   - **Решение через RAG-бот:**
     - Единая точка доступа ко всем источникам (GitHub, Confluence, PDF, Google Drive, Zendesk)
     - Объединение разрозненных документов через векторный поиск
     - Выявление дубликатов и расхождений через сравнение семантически похожих документов
     - Аналитика по частоте запросов для оценки важности документации
     - Метаданные для отслеживания версий и источников

2. **Время поиска:**
   - **Проблема:** Новые инженеры тратят до 4 часов в неделю на поиск решений. Одни и те же вопросы задаются повторно.
   - **Решение через RAG-бот:**
     - Мгновенный поиск по всей базе знаний (секунды вместо часов)
     - Кэширование частых запросов
     - История запросов для выявления повторяющихся вопросов
     - Персонализация ответов для разных ролей
     - **Ожидаемый эффект:** Сокращение времени поиска с 4 часов/неделю до ~10-15 минут/неделю (экономия ~3.5 часов/неделю на сотрудника)

3. **Жизненный цикл контента:**
   - **Проблема:** У страниц нет единого владельца. После major-release документация устаревает через 2-3 месяца.
   - **Решение через RAG-бот:**
     - Автоматическое выявление устаревшей документации через сравнение с актуальными источниками
     - Отслеживание метаданных (даты создания, обновления, версии)
     - Интеграция с CI/CD для автоматического обновления индекса после релизов
     - Уведомления о расхождениях между версиями документов
     - Аналитика по актуальности документации

4. **Соответствие аудитам:**
   - **Проблема:** Подготовка к SOC 2 yearly review занимает ~140 часов работы GRC-команды из-за ручной сверки актуальных политик.
   - **Решение через RAG-бот:**
     - Автоматическая сверка политик и регламентов
     - Выявление актуальных версий документов
     - Генерация отчетов о соответствии требованиям
     - Отслеживание изменений в политиках через метаданные
     - **Ожидаемый эффект:** Сокращение времени подготовки к аудиту с 140 часов до ~20-30 часов (экономия ~110 часов)

**Решение, которое нужно создать:**

Интеллектуальный бот на основе RAG, который должен:
1. **Быстро и точно давать персонализированные ответы** на вопросы сотрудников на основе базы знаний
2. **Выявлять пробелы в документации** - определять темы, которые не покрыты текущими материалами
3. **Помогать системно улучшать качество документации** - анализировать запросы, выявлять устаревшую информацию, предлагать улучшения
4. **Использовать технологии RAG** (Retrieval-Augmented Generation) для точного поиска и генерации ответов
5. **Применять продвинутые техники промптинга** для улучшения качества ответов

**Цели бизнеса в контексте внедрения RAG-бота:**

1. **Сократить затраты на поиск информации и коммуникацию внутри команды:**
   - Уменьшить время самостоятельного поиска и обращений к коллегам
   - Прямая экономия рабочего времени и сокращение затрат на FTE
   - **Как решение это достигает:** Мгновенный поиск вместо часов, кэширование частых запросов, снижение нагрузки на экспертов

2. **Повысить продуктивность сотрудников:**
   - Быстрый доступ к актуальным и точным знаниям
   - Ускорение выполнения задач, принятия решений и онбординга
   - **Как решение это достигает:** Персонализированные ответы по ролям, интеграция с CI/CD для актуальности, оптимизация для новых сотрудников

3. **Автоматизировать повторяющиеся операции и запросы:**
   - Снизить нагрузку на тимлидов, старших разработчиков и поддержку
   - Автоматический ответ на часто задаваемые вопросы
   - **Как решение это достигает:** Кэширование FAQ, история запросов, автоматические ответы на типовые вопросы

4. **Выявить и устранить пробелы в корпоративной документации:**
   - Системно пополнять документацию по непокрытым темам
   - Использовать аналитику для улучшения базы знаний
   - **Как решение это достигает:** Анализ неотвеченных запросов, семантический анализ покрытия, автоматические рекомендации

5. **Улучшить качество внутренних процессов и знаний:**
   - Повысить уровень формализации и актуальности документации
   - Создать конкурентное преимущество через качественную базу знаний
   - **Как решение это достигает:** Автоматическое выявление устаревшей информации, метрики качества, регулярные отчеты

6. **Создать масштабируемое решение для переиспользования:**
   - Масштабирование на другие команды и проекты
   - Возможность предлагать как продукт внешним клиентам
   - **Как решение это достигает:** Модульная архитектура, интеграция с AWS EKS, поддержка множественных источников

7. **Поддерживать рост и устойчивость бизнеса:**
   - Инфраструктура знаний без деградации при росте компании
   - Адаптация к изменениям в структуре и процессах
   - **Как решение это достигает:** Горизонтальное масштабирование в EKS, инкрементальные обновления, гибкая архитектура

**Ключевые требования:**
- Конфиденциальность данных (часть материалов не должна уходить в облако)
- Интеграция с существующей AWS инфраструктурой (EKS)
- Масштабируемость решения с учетом роста 400 страниц/месяц
- Поддержка множественных источников данных (GitHub, Confluence, PDF, Google Drive, Zendesk)
- Персонализация ответов для разных ролей пользователей
- Снижение затрат на поиск информации
- Выявление пробелов в документации
- Системное улучшение качества документации через аналитику

<summary><strong>Обоснование цифр</strong></summary>

**Локальные модели (Hugging Face):**
- **Модели:** Llama 3, Mistral и другие доступны через Hugging Face Hub (huggingface.co)

- **Операционные затраты:** Электроэнергия для GPU сервера ~$200-500/месяц, инфраструктура ~$100-300/месяц (источник: типичные затраты на дата-центр)
- **Скорость:** Бенчмарки Llama 3 на A100 показывают 30-50 токен/сек для 8B, 10-20 для 70B (источник: официальные бенчмарки Meta)

**Облачные модели:**
- **OpenAI цены:** Официальные цены OpenAI API (источник: openai.com/pricing, ноябрь 2024)
  - GPT-4: $0.03/1K входных, $0.06/1K выходных токенов
  - GPT-3.5-turbo: $0.0015/1K входных, $0.002/1K выходных токенов
  - Расчет: 1000 запросов/день × 500 токенов (250 входных + 250 выходных) = 500K токенов/день
- **YandexGPT цены:** Официальные цены Yandex Cloud (источник: cloud.yandex.ru, ноябрь 2024)
  - YandexGPT Pro: ~₽0.15/1K токенов (~$0.0015-0.002 при курсе ~100₽/$)
  - YandexGPT Lite: ~₽0.08/1K токенов
- **Скорость:** Измерения на основе реальных API запросов и документации провайдеров

## 4. Рекомендуемая конфигурация сервера

### Учет текущей архитектуры QuantumForge Software

Компания уже использует **AWS (EKS + RDS)**, что позволяет:
- Развернуть RAG-бот как микросервис в существующем EKS кластере
- Использовать существующую инфраструктуру мониторинга и CI/CD
- Интегрироваться с существующими сервисами через API
- Использовать AWS сервисы для хранения и бэкапов

### Расчет требований к ресурсам

**Текущий объем данных:**
- ~21,250 документов
- Средний размер документа: ~1000 токенов
- Размер эмбеддинга (multilingual-e5-base, 768 dim): ~3 KB на документ
- Общий размер векторной БД: ~64 MB (текущий объем)
- С метаданными и индексами: ~200-300 MB

**Прогноз роста:**
- Через 1 год: ~26,050 документов (~80 MB векторов, ~250-400 MB с метаданными)
- Через 3 года: ~35,650 документов (~110 MB векторов, ~350-550 MB с метаданными)

**Требования к памяти:**
- Векторная БД в памяти: ~300 MB (текущий) → ~550 MB (через 3 года)
- Модель эмбеддингов: ~600 MB (multilingual-e5-base)
- Буферы и кэш: ~2-4 GB
- **Итого RAM**: Минимум 4-8 GB, рекомендуется 16-32 GB для комфортной работы

### Конфигурации для развертывания

#### Минимальная конфигурация (для тестирования/разработки)
- **CPU**: 4-8 ядер (Intel i5/i7 или AMD Ryzen 5/7)
- **RAM**: 16-32 GB
- **GPU**: Не требуется (можно использовать CPU)
- **Storage**: 100 GB SSD
- **Стоимость**: ~$500-800 (on-premise) или ~$50-100/месяц (AWS EC2)

#### Рекомендуемая конфигурация для AWS EKS (для продакшена)
- **CPU**: 8-16 vCPU (AWS: m5.2xlarge или m5.4xlarge)
- **RAM**: 32-64 GB
- **GPU**: Не требуется (используются облачные API для LLM)

     - **Новых сотрудников** (onboarding-инструкции)

**Расчет производительности для текущих объемов:**
- Поиск: ~5-20ms для ~21,250 документов (достаточно быстро)
- Индексация: ~85 секунд для полной переиндексации (выполняется редко)
- Инкрементальное обновление: ~0.4 секунды для 400 новых документов/месяц

FAISS был бы предпочтительнее только при очень больших объемах (>10M векторов) или при необходимости максимальной производительности поиска (<1ms), что не является приоритетом для текущих объемов QuantumForge Software. ChromaDB обеспечивает лучший баланс между производительностью, удобством использования и поддержкой метаданных для множественных источников.
