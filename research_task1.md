# Задание 1: Исследование моделей и инфраструктуры для RAG-бота

## Контекст задачи

QuantumForge Software — финско-эстонская продуктовая компания, которой требуется интеллектуальный бот для работы с корпоративной базой знаний:
- ~18,000 Markdown/MDX файлов в репозиториях
- ~3,000 страниц Confluence (30 пространств)
- ~250 PDF-спецификаций
- Прирост ~400 страниц в месяц

**Текущая архитектура компании:**

| Слой | Технологии и сервисы | Где лежат документы |
|------|---------------------|---------------------|
| Продакшн | AWS (EKS + RDS) + облачные технологии (фронтовые edge‑ноды) | Terraform state, Helm charts |
| CI/CD | GitHub Actions, Jenkins (legacy), ArgoCD | GitHub Wiki, README |
| Общение | Slack, Jira, Confluence, Miro | Confluence, Google Drive |
| Код | Monorepo (GitHub); microservices на Python/Go/Node | CODEOWNERS, ADR (Markdown) |
| Данные | Kafka, ClickHouse, Snowflake | dbt‑доки, ER‑диаграммы |
| Служба поддержки | Zendesk + Statuspage | Zendesk Guide, Google Docs |

**Источники документов для RAG-бота:**
1. **GitHub** - 18,000 Markdown/MDX файлов (monorepo, CODEOWNERS, ADR, README, GitHub Wiki)
2. **Confluence** - 3,000 страниц (30 пространств)
3. **PDF-файлы** - 250 спецификаций (наследие заказных проектов)
4. **Google Drive** - дополнительные документы
5. **Zendesk Guide** - документация службы поддержки
6. **Google Docs** - регламенты и бизнес-правила

**Динамика роста:**
- Текущий объем: ~21,250 документов (18,000 + 3,000 + 250)
- Прирост: ~400 страниц/месяц
- Прогноз через год: ~26,050 документов
- Прогноз через 3 года: ~35,650 документов

**Ключевые требования:**
- Конфиденциальность данных (часть материалов не должна уходить в облако)
- Интеграция с существующей AWS инфраструктурой (EKS)
- Масштабируемость решения с учетом роста 400 страниц/месяц
- Поддержка множественных источников данных (GitHub, Confluence, PDF, Google Drive, Zendesk)
- Снижение затрат на поиск информации
- Выявление пробелов в документации

## 1. Сравнение LLM-моделей

### 1.1 Локальные модели (Hugging Face)

#### Популярные модели:
- **Llama 2/3** (7B, 13B, 70B параметров)
- **Mistral 7B**
- **Zephyr 7B**
- **Phi-2/3**

#### Качество ответов
- **Оценка: 7/10**
- Хорошее качество для специализированных задач при правильной настройке
- Требуют fine-tuning для корпоративного домена
- Могут галлюцинировать, особенно модели меньшего размера (7B)
- Модели 13B+ показывают значительно лучшее качество, но требуют больше ресурсов

#### Скорость работы
- **Оценка: 6/10**
- Зависит от размера модели и наличия GPU
- На CPU: 1-5 токенов/сек для 7B моделей, неприемлемо медленно для 13B+
- На GPU (например, A100): 20-50 токенов/сек для 7B, 10-20 для 13B
- Латентность первого токена: 0.5-2 секунды на GPU

#### Стоимость владения и использования
- **Оценка: 8/10**
- **Разовые затраты:**
  - GPU сервер (A100 40GB): ~$10,000-15,000 или аренда ~$1-2/час
  - CPU сервер (32+ ядер, 128GB RAM): ~$3,000-5,000
- **Операционные затраты:**
  - Электроэнергия: ~$200-500/месяц для GPU сервера
  - Инфраструктура: ~$100-300/месяц
- **Масштабирование:** Линейно с количеством запросов (нужны дополнительные GPU)
- **При больших объемах:** Может быть дешевле облачных решений

#### Удобство и простота развёртывания
- **Оценка: 5/10**
- Требует настройки инфраструктуры (GPU/CPU серверы)
- Необходимо управление версиями моделей
- Требуется мониторинг производительности и ресурсов
- Сложнее масштабировать при росте нагрузки
- Полный контроль над данными и конфиденциальностью

- GPT-3.5-turbo: Хорошее качество для большинства задач
- YandexGPT: Хорошее качество, лучше работает с русским языком
- Постоянно улучшаются без необходимости обновления инфраструктуры

- **Оценка: 9/10**
- Быстрая генерация: 20-100 токенов/сек
- Низкая латентность: 0.3-1 секунда
- Автоматическое масштабирование под нагрузку
- Нет проблем с холодным стартом

#### Стоимость владения и использования

- **OpenAI GPT-4**: ~$0.03/1K входных токенов, ~$0.06/1K выходных
- **OpenAI GPT-3.5-turbo**: ~$0.0015/1K входных, ~$0.002/1K выходных
- **YandexGPT Pro**: ~₽0.15/1K токенов
- **Пример расчета для 1000 запросов/день (средний запрос 500 токенов):**
  - GPT-3.5-turbo: ~$0.75/день = ~$22.5/месяц
  - GPT-4: ~$15/день = ~$450/месяц
- **При больших объемах:** Может быть дороже локальных решений
- **Преимущество:** Нет затрат на инфраструктуру и обслуживание

#### Удобство и простота развёртывания
- **Оценка: 10/10**
- Простое API, быстрое внедрение
- Не требует управления инфраструктурой
- Автоматическое масштабирование
- Регулярные обновления моделей
- **Недостаток:** Данные отправляются в облако (проблема конфиденциальности)

## 2. Сравнение моделей эмбеддингов

### 2.1 Локальные модели (Sentence-Transformers)

#### Популярные модели:
- **all-MiniLM-L6-v2** (22MB, 384 размерность)
- **all-mpnet-base-v2** (420MB, 768 размерность)
- **multilingual-e5-base** (560MB, 768 размерность) - для мультиязычности

#### Скорость создания индекса
- **Оценка: 8/10**
- **all-MiniLM-L6-v2**: ~1000 документов/сек на CPU, ~5000/сек на GPU
- **all-mpnet-base-v2**: ~300 документов/сек на CPU, ~2000/сек на GPU
- **multilingual-e5-base**: ~250 документов/сек на CPU, ~1500/сек на GPU
- Для текущего объема (~21,250 документов):
  - MiniLM: ~21 секунд на CPU
  - mpnet: ~71 секунд на CPU
  - multilingual-e5: ~85 секунд на CPU
- Для прироста 400 документов/месяц: ~0.4-1.6 секунд на CPU (в зависимости от модели)
- Индексация может выполняться пакетно, не требует постоянного подключения
- Инкрементальное обновление индекса эффективно для ежемесячных обновлений

#### Качество поиска
- **Оценка: 7/10**
- **all-mpnet-base-v2**: Лучшее качество для английского языка
- **multilingual-e5-base**: Хорошее качество для мультиязычных данных
- **all-MiniLM-L6-v2**: Хороший баланс скорость/качество
- Качество сопоставимо с облачными для большинства задач
- Можно fine-tune под специфический домен

#### Стоимость владения и использования
- **Оценка: 9/10**
- **Разовые затраты:** Модели бесплатны
- **Инфраструктура:** Работает на CPU, не требует GPU
- **Операционные затраты:** Минимальные (только сервер для индексации)
- **Масштабирование:** Очень дешево, можно запускать на обычных серверах
- **При больших объемах:** Значительно дешевле облачных решений

### 2.2 Облачные модели (OpenAI Embeddings)

#### OpenAI text-embedding-3-small/large
- **text-embedding-3-small**: 1536 размерность

- Может быть медленнее при больших объемах из-за необходимости батчинга
- Инкрементальное обновление требует повторной индексации измененных документов

#### Качество поиска
- **Оценка: 9/10**
- Отличное качество, особенно для сложных запросов
- Хорошо работает с контекстом и семантикой
- text-embedding-3-large показывает лучшее качество
- Постоянно улучшается

#### Стоимость владения и использования
- **Оценка: 6/10**
- **text-embedding-3-small**: $0.02/1M токенов
- **text-embedding-3-large**: $0.13/1M токенов
- **Пример для текущего объема (~21,250 документов, средний размер 1000 токенов):**
  - small: ~$0.43 за первоначальную индексацию
  - large: ~$2.76 за первоначальную индексацию
- **Ежемесячные затраты на обновление (400 новых документов):**
  - small: ~$0.008/месяц
  - large: ~$0.052/месяц
- **Годовые затраты на обновления (4,800 новых документов):**
  - small: ~$0.10/год
  - large: ~$0.62/год
- **При больших объемах и частых обновлениях:** Может быть дорого
- **Преимущество:** Нет затрат на инфраструктуру

## 3. Сравнение векторных баз данных

### 3.1 FAISS (Facebook AI Similarity Search)

#### Скорость поиска и индексации
- **Оценка: 9/10**
- **Поиск:** Очень быстрый, особенно с GPU
  - CPU: ~1-10ms для поиска в 1M векторов
  - GPU: ~0.1-1ms для поиска в 1M векторов
- **Индексация:** Быстрая
  - CPU: ~1-5 секунд для 100K векторов
  - GPU: ~0.1-1 секунда для 100K векторов
- Поддерживает различные типы индексов (IVF, HNSW, Flat)
- Оптимизирован для больших объемов данных

#### Сложность внедрения и поддержки
- **Оценка: 6/10**
- **Внедрение:** Средняя сложность
  - Требует настройки индекса (выбор типа, параметров)
  - Нужно управлять персистентностью (сохранение/загрузка)
  - Требует написания обертки для интеграции с приложением
- **Поддержка:** Средняя сложность
  - Нужно управлять версиями индексов
  - Требуется мониторинг производительности
  - Обновление индекса требует пересоздания (для некоторых типов)

#### Удобство в работе
- **Оценка: 5/10**
- Низкоуровневая библиотека, требует больше кода
- Нет встроенной поддержки метаданных (нужно хранить отдельно)
- Нет встроенной версионизации
- Требует ручного управления персистентностью
- Хорошая интеграция с Python через langchain

#### Стоимость владения
- **Оценка: 9/10**
- **Библиотека:** Бесплатная (open-source)
- **Инфраструктура:** Минимальная
  - Может работать на CPU (достаточно для средних объемов)
  - GPU опционально для очень больших объемов
- **Хранение:** Эффективное использование памяти
- **Масштабирование:** Очень дешево, можно запускать на обычных серверах

### 3.2 ChromaDB

#### Скорость поиска и индексации
- **Оценка: 8/10**

  - ~5-20ms для поиска в 1M векторов (зависит от конфигурации)
  - Использует HNSW индекс под капотом
- **Индексация:** Средняя скорость
  - ~5-15 секунд для 100K векторов
  - Автоматическая оптимизация индекса
- Хорошая производительность для большинства случаев использования

#### Сложность внедрения и поддержки
- **Оценка: 9/10**
- **Внедрение:** Очень простое
  - Простой Python API
  - Автоматическое управление индексами
  - Встроенная персистентность
  - Хорошая интеграция с langchain
- **Поддержка:** Простая
  - Автоматическое управление версиями коллекций
  - Встроенный мониторинг
  - Простое обновление данных

#### Удобство в работе
- **Оценка: 9/10**
- Высокоуровневый API, очень удобный
- Встроенная поддержка метаданных
- Автоматическое управление персистентностью
- Поддержка фильтрации по метаданным
- Хорошая документация и примеры
- Можно запускать как сервис или встроенно

#### Стоимость владения
- **Оценка: 8/10**
- **Библиотека:** Бесплатная (open-source)
- **Инфраструктура:** Минимальная
  - Может работать на CPU
  - Требует немного больше памяти, чем FAISS (из-за метаданных)
- **Хранение:** Эффективное, но немного больше, чем FAISS
- **Масштабирование:** Хорошее, можно запускать на обычных серверах
- **Дополнительно:** Есть облачная версия (платная) для масштабирования

## 4. Рекомендуемая конфигурация сервера

### Учет текущей архитектуры QuantumForge Software

Компания уже использует **AWS (EKS + RDS)**, что позволяет:
- Развернуть RAG-бот как микросервис в существующем EKS кластере
- Использовать существующую инфраструктуру мониторинга и CI/CD
- Интегрироваться с существующими сервисами через API
- Использовать AWS сервисы для хранения и бэкапов

### Расчет требований к ресурсам

**Текущий объем данных:**
- ~21,250 документов
- Средний размер документа: ~1000 токенов
- Размер эмбеддинга (multilingual-e5-base, 768 dim): ~3 KB на документ
- Общий размер векторной БД: ~64 MB (текущий объем)
- С метаданными и индексами: ~200-300 MB

**Прогноз роста:**
- Через 1 год: ~26,050 документов (~80 MB векторов, ~250-400 MB с метаданными)
- Через 3 года: ~35,650 документов (~110 MB векторов, ~350-550 MB с метаданными)

**Требования к памяти:**
- Векторная БД в памяти: ~300 MB (текущий) → ~550 MB (через 3 года)
- Модель эмбеддингов: ~600 MB (multilingual-e5-base)
- Буферы и кэш: ~2-4 GB
- **Итого RAM**: Минимум 4-8 GB, рекомендуется 16-32 GB для комфортной работы

### Конфигурации для развертывания

#### Минимальная конфигурация (для тестирования/разработки)
- **CPU**: 4-8 ядер (Intel i5/i7 или AMD Ryzen 5/7)
- **RAM**: 16-32 GB
- **GPU**: Не требуется (можно использовать CPU)
- **Storage**: 100 GB SSD
- **Стоимость**: ~$500-800 (on-premise) или ~$50-100/месяц (AWS EC2)

#### Рекомендуемая конфигурация для AWS EKS (для продакшена)
- **CPU**: 8-16 vCPU (AWS: m5.2xlarge или m5.4xlarge)
- **RAM**: 32-64 GB
- **GPU**: Не требуется (используются облачные API для LLM)
- **Storage**: 
  - EBS: 200-500 GB SSD (gp3) для векторной БД
  - S3: для бэкапов и архивов
- **Стоимость**: ~$300-600/месяц (AWS EC2/EKS)
- **Дополнительно**: 
  - EKS кластер (если еще не развернут): ~$72/месяц
  - Load Balancer: ~$20-30/месяц
  - Мониторинг (CloudWatch): ~$50-100/месяц

#### Масштабируемая конфигурация (для роста до 3 лет)
- **CPU**: 16-32 vCPU (AWS: m5.4xlarge или m5.8xlarge)
- **RAM**: 64-128 GB
- **Storage**: 500 GB - 1 TB SSD
- **Стоимость**: ~$600-1,200/месяц (AWS)
- **Горизонтальное масштабирование**: Возможно через EKS (2-3 реплики)

#### Для полностью облачного решения (без локальной инфраструктуры)
- **CPU**: 4-8 vCPU
- **RAM**: 16-32 GB
- **GPU**: Не требуется (используются облачные API)
- **Storage**: 100-200 GB
- **Стоимость**: ~$50-200/месяц (зависит от провайдера)

### Вариант 4: Оптимизированное решение с интеграцией в AWS EKS (рекомендуемое для QuantumForge)

**Конфигурация:**
- **LLM**: YandexGPT (облако) - для качества, с возможностью перехода на локальную модель
- **Эмбеддинги**: multilingual-e5-base (локально в EKS, Sentence-Transformers) - для мультиязычности
- **Векторная БД**: ChromaDB (локально в EKS) - для удобства и метаданных
- **Инфраструктура**: AWS EKS (m5.2xlarge или m5.4xlarge), 32-64 GB RAM, без GPU
- **Хранилище**: EBS gp3 для векторной БД, S3 для бэкапов

   - Простое развертывание в Kubernetes
   - Хорошая производительность для текущих объемов (~21,250 документов)

## Итоговый выбор векторной БД

**Выбрана: ChromaDB**

**Обоснование:**
1. **Удобство использования:** Высокоуровневый API, простая интеграция с langchain и Kubernetes
2. **Метаданные:** Встроенная поддержка метаданных критична для работы с разными типами документов:
   - GitHub: метаданные о репозитории, пути, авторах, датах коммитов
   - Confluence: метаданные о пространствах, страницах, версиях
   - PDF: метаданные о проектах, датах создания, авторах
   - Zendesk: метаданные о категориях, статусах, датах обновления
   - Google Drive: метаданные о типах файлов, владельцах, датах изменения
3. **Поддержка:** Проще в поддержке и обновлении, чем FAISS
4. **Производительность:** Достаточна для текущих объемов (~21,250 документов) и прогнозируемого роста до ~35,650 документов через 3 года
5. **Масштабируемость:** Легко масштабировать при росте 400 страниц/месяц через горизонтальное масштабирование в EKS
6. **Локальное развертывание:** Можно развернуть в EKS для конфиденциальности
7. **Инкрементальные обновления:** Эффективная поддержка обновлений индекса при добавлении новых документов
8. **Интеграция с AWS:** Хорошо работает с EBS для персистентности, S3 для бэкапов

**Расчет производительности для текущих объемов:**
- Поиск: ~5-20ms для ~21,250 документов (достаточно быстро)
- Индексация: ~85 секунд для полной переиндексации (выполняется редко)
- Инкрементальное обновление: ~0.4 секунды для 400 новых документов/месяц

FAISS был бы предпочтительнее только при очень больших объемах (>10M векторов) или при необходимости максимальной производительности поиска (<1ms), что не является приоритетом для текущих объемов QuantumForge Software. ChromaDB обеспечивает лучший баланс между производительностью, удобством использования и поддержкой метаданных для множественных источников.
